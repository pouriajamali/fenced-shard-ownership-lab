# ADR-001: Separate ownership, fencing and business idempotency

Status: accepted for this bounded lab; no production applicability claim.

## Context and choice

One synthetic shard has competing workers. A paused worker can resume after its lease expires. Electing another worker does not revoke an already delayed external write. A timeout after effect commit also does not tell the caller whether an effect happened.

Use existing etcd consensus for acquired-key creation revisions, PostgreSQL as the single authoritative sink, and durable business operation identities independent of generation. The sink transaction serializes on one shard state row. It atomically enforces the high-water fence, uniqueness, request digest, resulting total and stored receipt. Committed activation defines cutover. A new owner can replay a previously committed business result, but cannot reuse its identity with another payload.

## Alternatives and consequences

| Alternative | Decision |
| --- | --- |
| Lease/election without sink enforcement | Rejected: a paused/in-flight old request can outlive a lease. |
| Deduplication by generation plus request ID | Rejected: retry under a new generation can create a second effect. |
| Homegrown consensus/lock-free engine | Rejected: not necessary to test this failure boundary. |
| Unconditional retry after timeout | Rejected: outcome can be unknown; resolve the same business identity. |
| Generic community etcd wrapper | Avoided for this scope; the small gateway surface has explicit tested bounds. It is not a general SDK. |
| Distributed/multi-sink effect commit | Excluded: this contract has one transactional PostgreSQL sink. |

One database row deliberately limits parallelism. This is a clarity/correctness choice for a single shard, not a throughput result. Database unavailability prevents progress. Three members on one machine do not create physical fault-domain redundancy. Fences do not authenticate malicious callers.

## Review and handoff

Review gateway acquisition/renewal parsing separately from sink atomicity/idempotency and fixture/oracle design. Acceptance names are in FAILURE-MATRIX.md. Reviewers should reproduce the counterexample and inspect PostgreSQL history independently of the CLI's snapshot. These are proposed technical review responsibilities, not a claim that a real team or direct reports performed them.
